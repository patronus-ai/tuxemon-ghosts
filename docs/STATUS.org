* Deliverable, achieved

A portable, step-indexed trace format plus an offline executor for
Tuxemon. Given a seed, Tuxemon now replays byte-identically — verified
through a *completed* battle (capture, level-ups, experience, winnings,
and a clean exit of =CombatState= back to the world), at both a daytime
and a night-hour =clock_epoch=.

* What is still unmeasured

- *The spec's =world_state= widening commitment did not ship.* The
  spec's Known Limitations section states plainly: "~world_state~
  coverage is thin — serialization yields only ~factions_manager~ and
  ~menu_flags~. Widening it is in scope for S1." That widening did not
  happen — =tuxemon/save_system/save_state.py='s =WorldSave= still has
  exactly those two fields, confirmed by reading the class directly. What
  DID get widened this project (task 12) is a different subtree,
  =persistent_npc_state=, not =world_state= — see the next bullet for why
  that widening measures nothing on any trace this project can currently
  record. So, honestly: the =world_state= half of =state_of()='s digested
  surface is exactly as thin today as it was at the end of the spike: two
  fields, no wider. Anyone relying on =verify() == 0= to certify
  =world_state= coverage beyond faction standings and menu-unlock flags
  is relying on something this project never built.
- *Capture and evolution as their own scenarios.* The completed-battle
  measurement above exercises level-ups and winnings as a side effect of
  one battle route; nothing separately isolates capture or evolution as
  their own digest-stability scenario.
- *A trace that captures a RESOLVED battle mid-recording.*
  =boot_from_save= cannot restore mid-combat state (there is no
  serializer seam on =CombatState=), and a resolving battle needs
  ~4945+ steps from a cold boot — no golden trace covers this; it needs
  its own slow-tier golden.
- *Cross-platform reproducibility.* Untested. One machine (macOS
  26.6.1 arm64), one OS, one Python (3.12).
- *Combat internals.* =state_of()= covers the player's =NPCState=,
  =world_state=, =persistent_npc_state=, map, tile, facing, and the
  state-stack NAMES. It does NOT cover combat internals (turn count,
  opponent HP) — there is no serializer seam on =CombatState=. So
  =verify() == 0= certifies that the player-visible outcome reproduced,
  not that combat itself played out identically turn-by-turn.
- =persistent_npc_state= is plumbed and discriminates correctly (a
  dedicated test hand-flips a spawned NPC's =persistence= flag to prove
  it), but is =[]= on every currently-recordable trace: no NPC in
  =mods/tuxemon/db/npc/*.yaml= sets =persistence: true=. It adds no
  practical coverage today.
- =tuxemon/mission/mission.py:47= and =tuxemon/event/eventparser.py:52=
  still hold raw =uuid4()=, unreachable by any route this suite currently
  drives.
- Cancelled-between-frames deferred actions (patch 0005) never get
  =cleanup()= called on them. This matches upstream's existing behavior
  for the analogous case, and =EventAction.cancel()= has zero callers
  anywhere in the vendored tree, so it is latent, not live.
- *The shipped gate never reproduces the spec's own cross-=PYTHONHASHSEED=
  evidence.* The determinism spike (=docs/2026-08-25-determinism-spike.org=)
  demonstrated byte-identical digests "across two ~PYTHONHASHSEED~ values",
  which mattered because Python randomizes string/dict hashing per process
  by default — a digest that happened to depend on that would fail
  intermittently, not deterministically. But both Makefile test targets
  (=make test=, =make slow=) run =PYTHONHASHSEED=0=, unconditionally, so
  every =make check= run this project's gate performs pins the SAME hash
  seed every time; the spike's second-seed evidence is not re-exercised by
  anything CI or a contributor runs today. This is mitigated, not
  unfounded: =tuxghost/digest.py='s =_canonical= sorts every dict's keys
  before hashing and =json.dumps(..., sort_keys=True)= is used throughout
  =tuxghost=, so nothing in the digest pipeline should be reading raw
  dict/set iteration order in the first place — but that claim currently
  rests on code inspection, not on the suite actually varying the seed and
  observing the same digest twice. No second-hashseed run has been added
  to the Makefile as part of this fix wave; documenting the gap here is
  the honest alternative to quietly re-asserting evidence the shipped gate
  does not produce.
- *The test suite depends on mutable state OUTSIDE this repo*:
  =~/.tuxemon/cache/l18n/*.mo= (corrupted once by two concurrent test
  runs racing on the same file — do not run two full suites at once; see
  =CLAUDE.md=), and =~/.tuxemon/tuxemon.yaml='s =display.fps= (now guarded
  by an assertion at boot — a mismatched or non-positive =fps= raises a
  clear =ValueError= instead of silently producing a wrong first-frame
  =dt= or a bare =ZeroDivisionError= — but it is still an external input
  nothing in this repo controls).

** The digest's measured blind spot

On the =paper_town= fixture, 600 idle ticks leave =state_of()=
BYTE-IDENTICAL. =state_of= covers map, tile_pos, facing, state_stack
(NAMES only), npc_state, world_state and persistent_npc_state; none
advances on an idle =client.update(dt)=. What an idle tick *does*
change, all invisible to the digest: the harness's own scheduled-input
step cursor; the map renderer's per-step animation clocks
(=camera_manager.update= / =map_animations.update_all=); live state
internals beyond names; and event-engine timers in flight.
*Operational consequence*: any future "observation must not perturb
state" test needs a PENDING SCHEDULED INPUT, not an idle schedule, or it
proves nothing — this project already had one test built on the idle
version before that was caught.

** Settled end states cannot detect a perturbation in this game

Grid movement makes a tile an attractor, so a change to WHEN something
happens but not WHERE it ends is invisible to a final-digest comparison.
Measured: against an injected =client.update(1.0/60)= in the render
pass, per-step digest sequences diverged at step 1 and stayed diverged
through index 56 of 59 before re-converging — 56 differing steps that a
final-digest assertion alone would have read as identical. Three of this
plan's own gates had to be rewritten to compare SEQUENCES rather than
endpoints because of this.

** The agent's FRAMES are wall-clock dependent, and =clock_epoch= does not fix it

=pyscroll/data.py:132= (a third-party dependency, reached through
~MapRenderer~) drives tile animation from =time.time() * 1000=;
=pin_clock= pins the engine's own clock module (patch 0004), not =time=
inside a third-party package. Two back-to-back ~png()~ calls of the same
state differed about one run in three because of it. This does NOT
break trace replay — nothing pyscroll touches enters =state_of()=, and
inputs are ground truth once recorded — but it does mean the same agent
at the same seed and epoch can be shown two different images of the same
state, so a live model run is unreproducible for a reason that would
persist at temperature zero. Not fixed here, by choice: pinning
=time.time= process-wide would mean either vendoring pyscroll into the
patch series (=patches/= is not for that) or a global monkeypatch every
consumer inherits, for a guarantee (frame reproducibility) this project
never promised. See the spec's Known Limitations for the full reasoning.

*** Practical note on =--upscale=

The capture passed =--upscale 1=. The CLI's default is 4, which — layered
on =scaled_context()='s measured scale 5 — sends 5120x2880 PNGs that the
API downscales anyway. At scale 5 the drawn region already fills
1280x720 (see =tuxghost/observe.py='s =png= docstring), so upscaling
before sending buys nothing but bytes.

** Display scale: measured digest-neutral, real scale is 5

=headless_init= hardcodes =scale=1=; the real game computes
=int(1280 / 256)= (256 = =NATIVE_RESOLUTION[0]=) = *scale 5*, not the 4
an earlier draft of the spec and plan asserted unmeasured. At scale 5,
=tile_size (16,16) -> (80,80)=, and the visible camera shrinks from
roughly 80x45 tiles to roughly 16x9 — a human-comparable field of view.

Measured *digest-neutral*: per-step digest sequences over a 300-step
moving route (=DOWN=/=UP=/=RIGHT=, not idle — see the digest blind spot
above) are byte-identical at every index between an unscaled (=scale=1=)
and a scaled boot, re-confirmed independently in two separate processes
with matching sequence hashes. Because of this, agent runs can opt into
the scaled, human-FOV context (=run_agent(scaled=True)=, which the CLI
passes; the library default stays =False=) without affecting anything

** The CLI's exit codes: 0 or 2 for every anticipated precondition, 1 only for a genuine engine bug

=tuxghost agent= never returns exit 1 for anything it can anticipate —
there is nothing for a recording to diverge *from*, so no precondition
failure may report that code. A genuine internal engine invariant
failure is deliberately the one exception: it still exits 1, a visible
crash, rather than being laundered into a tidy "refused". (An earlier
version of this heading claimed "0 or 2 only, never 1" outright, which
its own next paragraph — "a genuine engine invariant failure stays a
visible crash" — already contradicted; reworded so the headline matches
the documented exception instead of being corrected by it two sentences
later.) Four separate exit-1 paths were found and closed
during Task 8: a dead =except ImportError= around =ClaudePolicy=
construction (the import is lazy, so a missing =anthropic= would have
escaped from deep inside =run_agent=); a =--policy replay= transcript
whose record is malformed *mid-run* (=ReplayPolicy= parses lazily inside
=decide()=, unlike =ScriptedPolicy= whose actions the CLI pre-parses); a
non-object line in a =--policy scripted= actions file; and an invalid
=--upscale=. The =run_agent= call is bounded by
=except (ValueError, TypeError)= for exactly those four cases —
deliberately not =Exception=, so a genuine engine invariant failure stays
a visible crash instead of being laundered into a tidy "refused".

A *fifth* exit-1 path was found by the whole-branch review (Important
#2) and closed the same way: =ClaudePolicy.decide= calls the =anthropic=

** Honest limits

- *Model sampling is not determinism.* A live =ClaudePolicy= run is not
  reproducible from seed alone — the same seed and prompts can yield
  different actions. What IS reproducible is the trace once recorded;
  that is the guarantee this project actually makes. =ReplayPolicy=
  exists so a model-driven run CAN be re-executed decision-for-decision
  from a captured transcript.
- *Rendered pixels are an unmeasured cross-platform surface.* Same
  single-machine caveat as S1 (macOS 26.6.1 arm64, Python 3.12, one SDL

  corrupt a trace — but a policy's behaviour could differ on another
  machine even where the trace format holds.

** Architecture: no new stepping loop, no new format writer

=seal()= composes four primitives that already existed —
=boot_from_save=, =install_schedule=, =run_steps= (with =execute='s own
per-step checkpoint hook) and =Recorder= — and adds no fifth. =run_steps=
remains *the* loop and =Recorder= remains *the* trace writer, which is
load-bearing rather than tidy: =tuxghost/trace.py='s =read()= neither
sorts nor validates same-step input ordering, so a trace written by
anything other than those writers could replay in file order. S3 never
writes a trace file directly.

=seal()= exists rather than reusing =run_agent= because =run_agent='s
scripted path starts its first action at step 0 and therefore cannot
express a lead-in — true of 1 of the 2 committed traces
(=walk_1234= waits 30 steps).

** Where =add_edge= lives now — a third option, not either of the spec's two

** =max_cost=: an addition the spec never mentioned

Nothing in the spec bounded how much an editor may grow a script, and
=HOLD_CAP=/=SETTLE_CAP= are 600 each — so a few thousand inserted actions
describes a multi-million-step candidate: hours of engine time inside one
uninterruptible =seal()= call. That is the same reasoning
=tuxghost/agent/types.py= gives for capping a single action at all, so
=optimize()= takes a *required* =max_cost= and treats an over-budget
candidate as a *rejected round*, not a crash. =seal()='s own =max_cost=
is optional and refuses *before booting anything*, raising =OverBudget=
(a =ValueError= subclass, so existing broad handlers keep working) so
that "this candidate was too expensive" stays distinguishable from "this
parent trace does not boot".

Two places deliberately do *not* pass =max_cost=, both pinned and both
commented against restoration: =optimize()='s round 0 (the parent is the
baseline, not a proposal — refusing it would leave the run with nothing
to compare against) and the CLI's closing re-seal of the winner. The
second was a real bug: passing =max_cost= there raised =OverBudget=
uncaught and exited *1* for a plain =--max-cost 400= against the
442-step parent.

** An honest negative: the winner's re-seal is unfalsifiable from the artifact

The CLI re-seals the winning script to stamp its lineage taint rather than
editing an already-sealed =Provenance= (which would make the CLI a second
trace writer). *Nothing observable in the resulting artifact distinguishes
that re-seal from a trace whose =Provenance= was patched after the fact.*
=Recorder.finish= never passes =recorded_at= — the only field that could
carry a wall-clock discriminator — and is otherwise a pure function of
the pinned seed/epoch and the reached state, so the only field differing
between the loop's best trace and the re-seal is =taints=, which is
exactly what a patch would set.

The re-seal still earns its keep: one trace writer, plus a free digest
re-check that the winning script still reaches the score the loop
recorded (a mismatch is a refusal, exit 2, reported as a determinism
failure rather than a bad edit). But no assertion over the file can prove
the re-seal happened, and none pretends to. Verified independently by two
reviewers; the claim was traced through =record.py=, =trace.py= and
=runner.py= rather than assumed.

** The CLI's refusals

=optimize= follows =agent='s contract exactly: *0 or 2 for every
anticipated precondition; 1 is reserved for a genuine engine bug*, since
=optimize=, like =agent=, has nothing to diverge *from*. The shipped
exit-2 list is longer than the spec's sketch and is enumerated in the
spec's CLI section. Two worth naming here:

- =--editor mutation= without =--seed= is refused (an unseeded run would
  be unreproducible while still *looking* reproducible), *and so is its
  converse* — any other editor *with* =--seed=. Refusing rather than
  silently dropping it: dropping would still leave a seed no editor ever
  used sitting in =run.json= and in the winner's lineage taint, recorded
  as if it had produced the run.
- The parent trace is read through =cli._read_trace_or_refuse=, the
  module's single trace-reading boundary, with =allow_mismatch=False=.
  The plan's own code used a bare =read()= under
  =except (OSError, Refused)=, which would have exited *1* ("diverged")
  for a parent that is merely not valid JSON
  (=json.JSONDecodeError=) or structurally malformed
  (=pydantic.ValidationError=) — neither of which is =OSError= or
  =Refused=.

unusable =--edits= (or =--model= on =mutation=/=scripted=) is still
silently ignored.

** Honest limits

- *No live =ClaudeEditor= capture exists.* Unlike S2 — which has a real
  =claude-sonnet-5= run committed as
  =tests/golden/claude_town_1234.tuxghost= — S3's =ClaudeEditor= has
  *never been run against a real model*. Its coverage is stub-client
  tests only (=tests/test_optimize_claude.py=): prompt shape, JSON-fence
  parsing, the malformed-reply and =AnthropicError= arms. So the claim
  "an LLM editor can optimize a trace" is *unmeasured for S3*; what is
  measured is that a dumb seeded mutator can, which is the baseline such
  a claim would have to beat. There is no S3 equivalent of S2's
  live-capture section below because there was no S3 live capture.

  *Until the final fix wave, that capture could not have been run
  honestly.* =tuxghost.cli._optimize= built =ClaudeEditor(model=model)=
  and the =optimize= parser had no =--goal= at all, so =ClaudeEditor.goal=
  was =""=, =build_prompt= skipped its =Goal:= line, and every real
  =--editor claude= run would have sent the action list, the end tile,
  the checkpoints and a bare ~Score (higher is better): [0.0, -2.0,
  -442.0]~ — no target, and no legend for the three numbers (measured;
  the pre-fix prompt is pasted in the final-fix report). The only claim
  the spec permits about this editor is a comparison against
  =MutationEditor= at the same parent, budget and objective, and that
  comparison would have pitted a blindfolded editor against a sighted
  seeded baseline. Now fixed both ways: =--goal= exists and mirrors
  =agent='s, an unset =--goal= derives ~"reach tile (X, Y) on map
  MAP"~ from =--objective=/=--target=, and =ReachTile.TERMS= is sent as
  the score tuple's legend. Pinned at the CLI level by
  =tests/test_optimize_cli.py::test_the_target_reaches_the_claude_editors_prompt=
  (a stub =anthropic= module records what was actually sent). *The live
  comparison itself is still unrun.*
- *The =anthropic= extra stays optional.* The import is lazy and gated on
  =--editor claude=, so a genuine engine crash on =--editor mutation=
  cannot have its traceback replaced by =ModuleNotFoundError=. The extra
  *is* installed in this venv (S2's live capture needed it); the gate
  does not depend on it.
- *=ReachTile= is a proxy and this is not a hedge.* See the two entries
  above: on the one parent that exists, it degenerated to "same place,
  fewer steps".
- *One parent, one objective, one editor, three seeds, one machine, under
  load.* The tuning sweep ran at 1-minute load averages of 13.7–33.1 from
  unrelated work in other repos, so its wall-clock column is not usable;
  CPU time and total engine steps sealed are the columns that mean
  anything. Details and the raw numbers are in the tuning note.
- *S3 renders nothing.* No =FrameRenderer=, no =scaled_context=, no
  frames in any run directory — by design, and the =CandidateResult= an
  editor sees carries no pixels.
- *A transient =AnthropicError= discards the whole run, and this is the
  one place the branch's containment philosophy stops.* Everything else
  an editor can do wrong is contained to a single round: a malformed
  reply, an out-of-range index, an over-budget script are all logged as
  rejected rounds and the loop continues. An =AnthropicError= is not —
  =_optimize='s gated =except Exception= arm sits OUTSIDE the loop, so a
  rate limit on round 19 of 20 exits 2 having written *no artifact at
  all*: no winner trace, no =optimize.jsonl=, no =run.json=, and 19
  rounds of engine time gone. That is correct in the sense that it
  matches =_agent='s contract and never reports an API problem as a
  divergence (exit 1) or as the editor's fault; it is a limit in the
  sense that nothing checkpoints the log as it goes. Closing it means
  streaming =optimize.jsonl= per round rather than at the end, which is a
  change to when the file is opened, not to the loop — *unmeasured, not
  attempted.*

*The three findings.*

1. =ClaudeEditor= was never told what it is optimizing toward. Details
   and the pre-fix prompt are under "Honest limits" above. Fixed BOTH

   shape is unchanged — the point was that what is written can be read.
   Note the =ClassVar=: it is not a dataclass field, so =__match_args__=

   action)= patterns still work (that positional coupling was on the
   deliberately-carried list and stayed there).

   =tests/test_optimize_runner.py='s module docstring ("=ReachTile='s

   measured: it *varies* (−2 down to −9) and has simply never *improved*

* Post-S5 — the keyboard button gap in the exporter, closed

Found while answering "what is left before we can collect traces". This
is a *defect fixed after S5's close-out*, not part of S5 as delivered.

*The bug, measured:* =tuxghost/vgbench.py='s =_button_names()= mapped six
buttons — =UP DOWN LEFT RIGHT A B=. Tuxemon defines fifteen. The
keyboard map =tuxemon/tuxemon/platform/platform_pygame/events.py= (its
=default_input_map=, line ~307) binds =pg.K_ESCAPE= to =buttons.BACK=
(16384) and binds *no key at all* to =START= or =SELECT=, which are
gamepad-only. =Recorder.observe= filters nothing and
=install_recording_events= records every input the session delivers, so
a human who opens the world menu once during =tuxghost play= puts =BACK=
into the trace — and =segments_of= then raised:

: KeyError: 16384

That trace was *permanently unexportable*. Every human-collected trace
was at risk, which is why this was fixed before any collection began.

*The fix, and why the alias is derived rather than chosen.* Upstream's
own =tuxemon/tuxemon/platform/tools.py= =keymap= gives =buttons.BACK=
and =buttons.START= the *identical* intention, =intentions.WORLD_MENU=.
So =BACK= exports under =START='s name — preserving what the input
*meant* rather than inventing a name their enum lacks — and the alias is
computed from that =keymap= at import, never hardcoded. If upstream ever
gives =BACK= a different intention, the aliasing stops on its own. This
is the same discipline =_button_names()= already followed for the six
direct names (read from =buttons=, never literals).

=START= (32) and =SELECT= (16) are now mapped directly; both are in
their schema's enum and both are gamepad-reachable.

*Unmappable buttons are REFUSED, never dropped.* =MOUSELEFT= (32768),
=X=, =Y=, =L1/L2/R1/R2=, =HOME=, and the text events =UNICODE= (20001)
and =BACKSPACE= (20002) have no videogamebench name. =segments_of= now
raises a =ValueError= naming the value and the step. Silently dropping
them was the tempting alternative and is wrong: a segment list missing
an input the trace contains would not reproduce the run it claims to
describe.

*Consequence, deliberate:* the mapping is now MANY-TO-ONE, so the
held-set comprehension must deduplicate or a segment holding =BACK= and
=START= together emits =["START", "START"]= and violates their schema's
=uniqueItems=. =_NAME_TO_BUTTON= is therefore built from the DIRECT
names only; the export is a *projection*, not a round trip. =.tuxghost=
remains the lossless artifact and import stays out of scope.

they pin*, per this project's non-negotiable rule:

*** Defect 2 — a space bar destroyed the whole recorded session

=tuxemon.platform.const.events= shares the =PlayerInput.button= channel
with real buttons — =QUIT= (20000), =UNICODE= (20001), =BACKSPACE=
(20002) — and a =UNICODE= event carries the typed CHARACTER as its
=value=, not a float. =Recorder.observe= filtered nothing, so pressing
SPACE put =(step, 20001, ' ')= into =_inputs=, and =finish()= died:

: pydantic_core.ValidationError: 27 validation errors for Trace
: inputs.245.2  Input should be a valid number, unable to parse string
:               as a number [input_value=' ', input_type=str]

*At write time, on quit* — after the session had been played. The whole
recording was lost. This is the same class of defect as the exporter
button gap fixed earlier the same day, one layer deeper: both came from
assuming the six overworld buttons were the only thing a human produces.

*Fixed by dropping non-button events and TAINTING the trace*
(=DROPPED_NON_BUTTON = "dropped_non_button_input"=). Dropping keeps the
session writable; the taint keeps it honest, because a run whose text
entry was discarded will not replay faithfully. =tuxghost.cli='s
=compare= already surfaces taints as findings, so this costs no new
reader. The value guard is separate from the button guard on purpose,
and =bool= is excluded explicitly — it is an =int= subclass, and
=float(True)= would silently record 1.0.

* Defect 3 — the windowed render was full of holes, and why

Found immediately after the two defects above, in the SAME manual
acceptance session: the human reported "there is a black tiling thing".

*Symptom:* windowed, the map draws with large blank rectangles where
sprites and many tiles should be. The player and every NPC are missing.
Opaque ground tiles survive; everything needing alpha does not.

*Root cause:* =build_track= called =boot_from_save= with no =context=, so
=build_client= fell through to =tuxghost.boot.headless_context()=
(=boot.py:202=), which calls =pg.display.set_mode()= a SECOND time. A
second =set_mode= invalidates every surface already converted against
the first display — so the real client's already-loaded sprites and
alpha tiles became garbage and drew as blank.

=boot_from_save= has accepted a =context= parameter all along, and
=tuxghost.play= passes it for the REAL session. =build_track= never
accepted one. Fixed by giving it the parameter and having =play= forward
the windowed context.

*This is the second, independent half of the hazard =play.py='s
"Ordering note 2" describes.* That note forces =tuxemon.graphics= and
=tuxemon.map.view= to bind the windowed SCALE before the ghost build
runs, and it works — measured this session, both modules bound at scale
5 matching the real context. It says nothing about the display being
re-created underneath them, which is this defect. Ordering note 2 was a
correct fix to a different problem that shares a cause.

*Measured, windowed, 120 steps, seed 1234, epoch 1787659200:*

| build_track called with | frame bytes | matches headless? |
|---+---+---|
| no context (the defect) | 18772 | no — visibly holed |
| a context (the fix) | 17302 | *byte-identical* |
| not called at all (control) | 17302 | byte-identical |

Each row reproduced TWICE. The track itself is unaffected either way:
177 frames, last =GhostFrame(spyder_paper_town.tmx, (16,14),
Direction.RIGHT)=.

** A wrong diagnosis, corrected — recorded because the correction is the point

The first hypothesis was that =tuxghost.observe='s =FrameRenderer= built
its compositing surface as a plain =pg.Surface= with no =.convert()=, so
display-format sprites blitted onto it wrongly. Adding =.convert()=
appeared to fix it: the frame went to 17302 bytes, byte-identical to the
headless control. That looked conclusive and was wrong.

Two checks killed it. =convert()= changes NOTHING measurable here —
=plain= and =convert= both report =bitsize 32=, masks
=(16711680, 65280, 255, 0)=, =flags 0=, =alpha None=, =colorkey None=,
=bytesize 4=, under both dummy and a real window. And re-running the
UNFIXED configuration twice produced the clean 17302 image both times.
The artifact had never been about =convert()=: the experimental script
that "proved" the fix had silently dropped the =build_track= call.

*A fix that works is not a diagnosis.* The confounder was invisible until
the unfixed case was re-run, which is the only reason it was caught.
=observe.py= was restored and is unchanged on disk.

** Why no headless test can catch this

=make check= runs entirely headless, where there is no first display to
invalidate, so BOTH paths render identically — the pixel evidence above
only exists windowed. A pixel assertion in the suite would pass whether
or not the bug were present: precisely the vacuous-test trap this
project keeps re-discovering.

So =test_build_track_reuses_a_given_context_instead_of_reinitialising=
asserts the CALL instead: given a context, =headless_context()= must not
be reached. Demonstrated to fail against the defect — dropping the
=context=context= forwarding gives =AssertionError: [1, 1]= (called
twice, not once) — with =track.py= confirmed byte-identical after
restore.
