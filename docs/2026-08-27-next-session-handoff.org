* Stream B — S4, ghost rendering

*Brainstorm before implementing.* What follows is what is already known, so
that conversation starts from facts.

** What already exists that S4 needs

- *The rendering seam is public and proven.* S2 established that a real
  =MapRenderer= installs through =BaseClient.set_renderer= and composites
  via upstream's =StateDrawer=, with *no engine patch*. The measurement
  that justified it: a stock =NullRenderer= frame sampled to *1* colour
  (pure black); the same call with a real =MapRenderer= sampled to *48*.
- *A ghost's path is derivable, though not stored.* A trace holds only
  =(step, button, value)= inputs — no positions. But replay is
  deterministic, so the track is recoverable by running it:
  =execute(trace, checkpoint=N, capture_states=True)= already samples
  =state_of=, which carries =map=, =tile_pos= and =facing=.
- =provenance.recorder= already distinguishes ="cu-agent"=,
  ="offline-agent"= and ="human"=, so a ghost can be labelled by origin.

** The two real obstacles

1. *There is no live mode to host a ghost.* Nothing in this project ever
   opens a window; every boot is headless with dummy SDL drivers, and
   =CLAUDE.md= requires that of *every* invocation that touches the
   client. Windowed play is a deliberate exception to that rule and is the
   human's call, not the implementer's.
2. *Step-indexed format meets a wall-clock player.* The format is
   step-indexed on purpose — =PlayerInput.timestamp= deliberately never
   enters it, and anything reading real time to decide what happens next
   is a determinism bug by this project's own rules. A human playing in
   real time is the one consumer that reintroduces wall clock. "Which
   trace step is the ghost on right now" needs an explicit, stated
   mapping; =step_rate= 60 makes one step ≈ one frame at 60 fps, but a
   machine that drops frames changes the ghost's apparent speed.

** Open questions for the brainstorm

- Does a ghost render *in a live windowed session* (needs obstacle 1
  resolved), or *into recorded frames* — a filmstrip or video of one trace
  with another overlaid? The second needs no windowed mode at all and may
  be the cheaper first cut.
- Translucency: does drawing a second, alpha-blended entity need a seventh
  patch, or does =npc_manager= plus =set_renderer= reach it the way S2's
  frame did? *Unmeasured.* Probe before designing.
- Does the ghost's position come from a pre-computed track (replay once,
  store positions) or from a second engine instance stepped alongside?
  The first is far cheaper and matches the deterministic-replay guarantee.
- What identifies a ghost to a viewer — the =model= field, the
  =recorder= kind, a name in =taints=?

* Running two sessions at once

Three real collision points, and one verified fix.

** The shared-state hazard, and how to defuse it

=CLAUDE.md= warns that the suite depends on =~/.tuxemon/cache/l18n/*.mo=,
which *two concurrent runs have corrupted before*. That is a
=$HOME=-level path, so it is shared even between two separate clones —
which would normally make parallel work unsafe.

*Verified this session*: Tuxemon's user directory follows =$HOME=.

#+begin_src bash
HOME=/tmp/tux-home-b python -c "from tuxemon.constants import paths; print(paths.USER_STORAGE_DIR)"
# -> /tmp/tux-home-b/.tuxemon
#+end_src

So give each parallel session its own =HOME= for engine runs. *Caveats,
both unverified end to end*: copy the real =~/.tuxemon/tuxemon.yaml= into
it first — =tuxghost.boot= asserts =display.fps= against =STEP_RATE= at
boot and raises a =ValueError= if it disagrees — and be aware that
overriding =HOME= wholesale also moves git config, ssh and tool caches, so
scope it to the gate command rather than exporting it globally. Only path
resolution was verified; a full suite under a redirected =HOME= was not.

The simplest alternative, if that proves fiddly: *serialise the gates.*
Each stream runs =make check-fast= only at task boundaries and the two
sessions agree not to overlap. The fast tier is under 4 minutes on a quiet
host, so this costs little.
