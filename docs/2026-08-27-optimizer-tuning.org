#+TITLE: How many rounds does the offline optimizer need? — measured
#+DATE: 2026-08-27

The S3 spec left =rounds= and =patience= as an open question
("Unmeasured"), and =tuxghost.optimize.runner.optimize= makes all four
bounds *required* arguments precisely so that no unmeasured default could
be mistaken for a measured one. This note is the measurement. It is the
raw table first and the reading of it second; a tuning note whose numbers
are gone is a claim, not a measurement.

* What was run

Nine runs, driven through the *real CLI* (not an in-process harness), one
at a time, sequentially:

#+begin_src bash
SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy PYTHONHASHSEED=0 \
./.venv/bin/python -m tuxghost.cli optimize \
  --trace tests/golden/claude_town_1234.tuxghost \
  --editor mutation --seed $S \
  --objective reach-tile --target spyder_paper_town.tmx:11,16 \
  --rounds $R --patience $R --max-rejections $R --max-cost 4000 \
  --checkpoint 64 \
  --out .../s${S}r${R}.tuxghost --run-dir .../s${S}r${R}
#+end_src

- Seeds $S ∈ {1, 2, 3}; budgets $R ∈ {8, 16, 32}.
- =--patience= and =--max-rejections= are deliberately set *equal to*
  =--rounds= so that neither can bind. This sweep therefore measures
  =rounds=; what it says about =patience= is *derived* from the same runs
  (see "What this says about =patience=") and is not an independent
  measurement of it.
- =--max-cost 4000= — roughly 9× the parent's 442 steps, high enough that
  no candidate in the sweep came near it. *Zero rounds were rejected in
  any of the nine runs*, for any reason.
- Parent: =tests/golden/claude_town_1234.tuxghost=, the committed
  live-model capture. 442 steps, ends at tile =[11, 14]= on
  =spyder_paper_town.tmx= with =state_stack == ['DialogState',
  'WorldState']=. Its =ReachTile(spyder_paper_town.tmx, (11, 16))= score
  is =(0.0, -2.0, -442.0)=.
- Commit: =c306465= (Task 11's fix round), on branch
  =impl/offline-optimizer=. Run dirs and winners were written to a
  scratch directory outside the repo; nothing here is committed except
  this note.

** The wall-clock column is contaminated and should not be quoted

This host carried a 1-minute load average of *13.7 to 33.1* throughout
the sweep, from four unrelated =gym-cua-lucidchart= pytest suites and a
VM in other repos — a different repo and a different venv, so no
=~/.tuxemon/cache/l18n= race and no violation of this project's
one-suite-at-a-time rule, but useless as a timing. The column is
reproduced above for completeness and because hiding it would be worse,
not because it is usable: seed 2 at 32 rounds took *114.16 s* real at
load 13.7 while seed 1 at the same budget took *54.99 s* at load 17.5.
Wall clock on this host is not measuring the optimizer.

=CPU= and =steps sealed= are the columns to read. Both scale cleanly and
sub-linearly in =rounds=:

| rounds | steps sealed (min–max) | CPU s (min–max) |
|--------+------------------------+-----------------|
|      8 | 3819–3919 | 18.74–20.27 |
|     16 | 6821–7056 | 25.73–28.24 |
|     32 | 11455–12892 | 42.76–53.74 |

Sub-linear because the mutator's accepted edits *shorten* the script:
later candidates are cheaper to run than earlier ones. A doubling of
=rounds= costs roughly 1.5–1.8× the engine steps, not 2×.

* Does the dumb mutator beat the parent at all? Yes — 9 runs out of 9

Plainly: *yes, at every budget tested, on every seed tested.* There is no
negative result to report on the question "does =MutationEditor= improve
anything".

| rounds | steps saved vs the 442-step parent (seeds 1 / 2 / 3) | as % |
|--------+------------------------------------------------------+------|
|      8 | 50 / 28 / 34 | 11% / 6% / 8% |
|     16 | 68 / 57 / 139 | 15% / 13% / 31% |
|     32 | 158 / 125 / 180 | 36% / 28% / 41% |

Two prior probes agree and are not superseded: Task 8 measured
=MutationEditor= at seeds 7, 8 and 9 all beating the same parent within
12 rounds (best rounds 10, 8, 10).

* The finding that actually matters: 32 rounds has NOT saturated

Look at the =best round= column. Every single run found its best
candidate at, or within four rounds of, its own cap:

| rounds | best round (seeds 1 / 2 / 3) |
|--------+------------------------------|
|      8 | 8 / 8 / 8 |
|     16 | 13 / 11 / 16 |
|     32 | 32 / 32 / 28 |

At =rounds = 8= all three seeds improved on the *very last round
available*. At 32, two of three did. Every one of the nine runs stopped
with =stop_reason == "rounds exhausted"= — never "patience exhausted",
never a rejection cap.

*So =rounds= is the binding constraint over this whole sweep, and this
sweep does not find its ceiling.* Doubling the budget kept buying
improvement at both doublings, with no sign of flattening. Anyone wanting
a recommended =rounds= for this parent should read this as "more than 32,
unmeasured how much more" — not as "32 is enough".

That is a real limit on what this note establishes. It measures that the
budget is the constraint; it does not measure where diminishing returns
start, because it never reached them.

* What this says about =patience= (derived, not measured)

=patience= never bound in this sweep by construction, so what follows is
*derived from the accepted-round lists above*, not independently
measured. For each run, the longest run of consecutive non-improving
rounds that was nevertheless *followed* by an improvement:

| seed | rounds | longest stale streak that still preceded an improvement |
|------+--------+--------------------------------------------------------|
|    1 |      8 | 6 |
|    2 |      8 | 5 |
|    3 |      8 | 6 |
|    1 |     16 | 6 |
|    2 |     16 | 5 |
|    3 |     16 | 6 |
|    1 |     32 | 6 |
|    2 |     32 | 9 |
|    3 |     32 | 10 |

*=patience = 10= is the smallest value that would not have truncated any
of these nine runs early.* A =patience= of 6 would have ended both 32-round
runs on seeds 2 and 3 before their best candidate was found — seed 3's
best came after a 10-round barren stretch, and it was the best result in
the entire sweep (262 steps, 41% off the parent).

The honest caveat: this is a *lower bound derived from runs where patience
never fired*. It says patience must be at least 10 not to have cut these
particular trajectories short. It cannot say whether a run stopped at
patience 10 would have found more later, because no run in this sweep was
ever stopped by patience at all.

* Three things the sweep confirmed about the objective, incidentally

** =ReachTile='s =distance= term varied, and never once improved

The =distance= term (the middle element of the score tuple) is *not*
constant across candidates — an earlier reading of the fixture said it
was frozen, and that is wrong. Measured distinct distance values per run:

| seed | rounds | distinct =-distance= values seen |
|------+--------+----------------------------------|
|    1 |      8 | -6, -4, -2 |
|    2 |      8 | -6, -2 |
|    3 |      8 | -6, -2 |
|    1 |     16 | -6, -4, -2 |
|    2 |     16 | -6, -5, -2 |
|    3 |     16 | -6, -2 |
|    1 |     32 | -6, -5, -4, -2 |
|    2 |     32 | -6, -5, -2 |
|    3 |     32 | -9, -7, -6, -5, -3, -2 |

The parent's own value is =-2=. *No candidate in any of the nine runs
ever scored better than =-2=.* The term moved only downward, and only for
mid-script edits that changed the route *before* the trailing dialogue
begins; an edit appended after that point cannot move the player at all,
because the =DialogState= on top of the stack swallows every input.

The operational consequence, which =docs/STATUS.org= also records: *all
60 accepted rounds in this sweep (excluding the nine round-0 baselines)
were accepted on the =steps= term.* The =distance= term acted purely as a rejecter. The acceptance
path where a distance improvement wins is therefore **untested by this
sweep, and untestable against this parent** — closing it needs a parent
fixture that does not end mid-dialogue.

The =map= term was =0.0= in all nine runs, every round: no candidate ever
wandered off =spyder_paper_town.tmx=.

Round 1 runs *438* steps where the parent ran 442 and reaches digest
=bc717075= — the parent's own digest, exactly. Rounds 8 through 32 range
from 408 steps down to 262 and *all* hash to =b97ebc7c=. That is a 146-step
spread with one digest.

This is the project's own attractor lesson (=docs/STATUS.org=, "Settled
end states cannot detect a perturbation in this game") landing on S3
directly and freshly measured here: *"the optimizer improved the trace"
can never be established from the final digest.* The burden falls
entirely on =steps= and on the per-checkpoint digest sequence, which is
why the spec's Validation section requires round-by-round score sequences
rather than final-best comparisons.

Round 32 is also a small proof that the loop requires *strictly* better:
it scored =(0, -2, -262)=, tying round 28's winner exactly, and was not
accepted.

** Zero rejected rounds in 9 runs / 168 proposals

=MutationEditor= emits only in-range values by construction, so
=validate_actions= never had to catch it, =apply_edits= never refused an
index, and no candidate approached =--max-cost 4000=. The rejection path
is exercised by =tests/test_optimize_runner.py=, not by this sweep — and
that is the correct division: a baseline mutator that spent rounds on
rejected proposals would still look like it ran.

* Recommendation, with its own limits attached

For this parent and =ReachTile=, on one machine:

- =--rounds=: *at least 32, and 32 is not the ceiling.* Nothing here
  measures where returns diminish; every budget tested was still buying
  improvement when it ran out. If a caller needs a single number to start
  from, 32 is the largest value measured to work, not a value measured to
  be sufficient.
- =--patience=: *at least 10.* Derived, not measured; a smaller value
  would have truncated 2 of the 9 runs before their best round. There is
  no upper guidance, because patience never fired.
- =--max-rejections=: *unmeasured.* Zero rounds were rejected in the whole
  sweep, so this sweep says nothing about it. =tests/test_optimize_runner.py=
  pins the mechanism; no measurement backs a value.
- =--max-cost=: *4000 was never approached.* The right value is a function
  of how long a single candidate may take, not of this sweep. For a
  442-step parent, 4000 bounds a candidate at ~9× the parent, which cost
  under a second of engine time per candidate here.
- =--checkpoint 64=: used throughout, unvaried, so its cost is not
  isolated by this sweep.

No default was adopted in the code as a result of this note. All four
bounds remain required arguments of =optimize()= and of the CLI, which is
the honest position while =rounds= has no measured ceiling.

* Limits of this measurement

- *One parent trace.* =claude_town_1234= is the only committed trace with
  a live-model provenance, and it ends mid-dialogue. Everything above
  about the =distance= term is a property of *that* fixture.
- *One objective.* =ReachTile= is a proxy for progress and openly so.
- *One editor.* =MutationEditor= is a deliberately dumb blind
  hill-climber that ignores both the candidate and the score it is handed.
  Nothing here measures =ClaudeEditor=; the point of these numbers is to
  be the baseline such a claim would have to beat.
- *One machine, under load.* macOS 26.6.1 arm64, Python 3.12, one SDL
  build, load average 13.7–33.1 from unrelated work throughout.
- *Three seeds.* Enough to show the result is not a single lucky draw;
  not enough for a distribution.
